用最通俗的语言，讲清楚这个项目在做什么、每一步怎么走、什么条件下走哪一步

一、这个项目到底在干什么？

你问 ChatGPT "什么是ETF？" 它能回答，但如果你问 "我们公司内部规定年假怎么休？" 它就不知道了。知识库系统就是给 AI 装上"你自己的资料库"，让它只根据你提供的文档来回答，不瞎编。

一句话总结

用户提问 → 系统从你的文档库里找相关段落 → 把找到的内容喂给 AI → AI 根据这些内容生成回答。

这个过程叫 RAG（Retrieval-Augmented Generation，检索增强生成）。

本项目的具体场景：面向"投资理财知识"（内置 20 份文档，覆盖 ETF、债券基金、可转债、基金定投、指数/货币基金、基金费用、复利、QDII、资产配置、基金分红、黄金、银行理财、REITs、个人养老金、止盈止损、打新等，含 txt / md / docx / pdf 四种格式），但架构与业务解耦，换成任意领域的文档都能用。

四、每个步骤的作用、输入输出和触发条件（核心）

系统由 LangGraph 编排成 7 个"节点"，每个节点是一个函数。真正值得初学者理解的，是每个节点干什么、什么条件下才走它、什么条件下跳过它。

4.1 节点总览表

节点通俗名字作用谁在做
assess前台判断判断问题类型和处理模式LLM（通义千问）
hybrid_search资料检索BM25 + 向量两路检索并融合HybridRetriever
rerank精排复审把候选段落按相关性重新排序，留 Top-5SimpleReranker / BGE
inject_memory回忆上下文注入短期 + 长期记忆，判断是否追问Short/LongTermMemory
generate_answer正式回答根据检索段落 + 记忆生成回答LLM
direct_answer快速回答不检索，直接回答简单问题LLM
store_memory存档把本轮问答写入短期 + 长期记忆Short/LongTermMemory

4.2 节点①：assess — 判断问题类型

调用 LLM，给问题"分类"和"定路线"。返回一个 JSON，里面有两个字段：query_type（问题类型）和 processing_mode（处理模式）。
输入：用户原始问题
输出：query_type + processing_mode（以及 reasoning 决策理由）

query_type 有 4 种：

类型含义例子
simple_qa简单问答，可直接回答"你好"、"今天星期几"
knowledge_retrieval需要查知识库"什么是ETF？"
comparative_analysis需要对比分析"ETF和指数基金哪个好？"
procedural_guide需要步骤指南"定投怎么操作？"

processing_mode 有 2 种：

模式含义后续走向
reactive（反应式）简单问题，直接回答走 direct_answer，跳过检索
deliberative（深思熟虑）需要查资料走 hybrid_search 检索链
LLM 返回的值如果不是合法值（比如返回了奇怪的东西），会强制回退成默认值：mode 默认 reactive，type 默认 simple_qa。这是防止流程卡死的兜底。

4.3 岔路口：路由（route_after_assess）

这是整个流程最关键的"岔路口"。根据上一步得到的 processing_mode，决定下一步走哪条路。
graph TD A["assess 判断完成"] --> Q{"processing_mode 是什么？"} Q -->|"deliberative
要查资料"| S["走检索链
hybrid_search"] Q -->|"reactive
简单问题"| D["走快速通道
direct_answer"] S --> R["rerank"] --> M["inject_memory"] --> G["generate_answer"] D --> ST["store_memory"] G --> ST ST --> END["输出"] style Q fill:#e74c3c,color:#fff style S fill:#3498db,color:#fff style D fill:#27ae60,color:#fff
条件：processing_mode == "deliberative" → 走检索链；否则（reactive）→ 走直接回答。这是唯一的硬性分流条件。
就像去医院挂号分诊：普通感冒（reactive）直接开点药；疑难杂症（deliberative）需要先做一堆检查（检索）再诊断。

4.4 节点②：hybrid_search — 混合检索

BM25 关键词检索 + 向量语义检索，两路同时搜，再用 RRF 公式把结果合并成一个候选集。
输入：用户问题
输出：fused_results（融合后的候选段落列表，约 Top-20）
只有 deliberative 模式才会走到这个节点。reactive 模式完全不经过这里。
两个专家同时找资料：一个按"字面关键词"找（BM25），一个按"意思"找（向量），最后把两人的结果合并投票，都推荐的排前面。

4.5 节点③：rerank — 精排

对候选集做"精细重排"，只保留最相关的 Top-5 喂给 AI。当前默认用 SimpleReranker（无需下载模型）。
输入：fused_results（候选集）
输出：reranked_results / final_docs（Top-5）
如果 fused_results 为空（一个候选都没有），会跳过重排，直接返回空结果，继续走后面的节点（避免对空列表报错）。
海选之后还有决赛。检索只是粗排，重排是让"复审官"把每个候选和问题放到一起仔细对比，排出最准的顺序。

4.6 节点④：inject_memory — 注入记忆

把三类上下文拼起来，为下一步生成回答做准备：短期记忆（本会话最近对话）、长期记忆（历史相似问题）、追问提示（判断是否在追问）。
输入：用户问题 + session_id
输出：合并后的记忆上下文文本（long_term_context 字段）

三个子步骤各有条件：

  • 短期记忆：只要当前会话有历史，就注入最近几轮对话。
  • 长期记忆：条件 只有 Elasticsearch 连接成功（is_connected）才会去搜索相似历史问题；连不上就跳过，不报错。
  • 追问判断：见下一节 4.7 的详细条件。

4.7 追问判断（is_follow_up）— 一组明确的启发式条件

系统怎么知道用户是在"追问上一轮话题"，还是在"开启新话题"？靠一组写死的判断规则：

判定为"追问"需要同时满足：
① 有历史对话记录（不是第一句）
② 历史里至少有一条用户提问
③ 新问题长度 < 15 个字
④ 新问题里包含指代词，如："那"、"这个"、"它"、"还有"、"吗"、"怎么"、"多少"、"为什么"、"然后" 等

任何一条不满足 → 判定为"新话题"（不是追问）。
你刚问"什么是ETF？"，接着问"手续费呢？"——只有 4 个字、带"呢"，系统就知道你在追问 ETF 的手续费，而不是随便什么手续费。

4.8 节点⑤：generate_answer / direct_answer — 生成回答

两条路在这里汇合，都由 LLM 生成回答，区别在于喂给 LLM 的东西不同。
路径给 LLM 的材料对应 Prompt
generate_answer（检索链）检索到的文档段落 + 记忆上下文 + 问题RAG_GENERATION_PROMPT（要求基于文档、不编造、标来源）
direct_answer（快速通道）仅短期记忆上下文 + 问题DIRECT_ANSWER_PROMPT（要求简洁回答）
deliberative → generate_answer（带文档）；reactive → direct_answer（不带文档）。二选一，不会同时走。

4.9 节点⑥：store_memory — 存储记忆

把本轮问答"存档"，方便以后参考。同时写两处。
输入：问题、回答、类型、检索到的文档ID
输出：无（副作用是写入记忆）
  • 短期记忆：无条件写入（内存），超容量自动淘汰最旧记录。
  • 长期记忆：条件 只有 ES 连接成功才写入；连不上就只写短期，打印提示。

五、模型框架详解：用到了哪些"大脑"

项目里一共有三类"模型"，分别在不同地方干活。理解它们的分工，是看懂模型框架的关键。

5.1 大语言模型（LLM）—— 通义千问 qwen3.7-max

这是系统的"大脑"，负责"看懂问题"和"写出回答"。它在三个地方被调用（外加评估时一个裁判）：

调用点任务输出
assess 节点判断问题类型 + 处理模式JSON（query_type、processing_mode）
generate_answer 节点根据检索文档生成正式回答自然语言文本
direct_answer 节点直接回答简单问题自然语言文本
评估裁判（可选）LLM-as-Judge 给回答质量打分分数 / 反馈

通过阿里云 DashScope API 调用，温度参数设 0.1（让回答更稳定、少随机）。

同一个人干三种活：前台判断来客身份（分类）、正式咨询（查资料后回答）、快速应答（闲聊）。

5.2 向量编码模型（Embedding）—— BGE-large-zh-v1.5

把中文文字变成一串数字（向量），用于语义检索。文字意思越接近，向量越接近。

当前状态：已接入 SentenceTransformer("BAAI/bge-large-zh-v1.5") 编码器，BM25 与向量检索会经 RRF 真正融合。首次运行会从 HuggingFace 下载约 1.3GB 模型到 D 盘。

5.3 重排序模型（Reranker）—— SimpleReranker / BGE-Reranker

对候选段落做"精排"。当前默认 SimpleReranker（基于关键词重叠打分，无需下载模型），可选 BGE-Reranker（交叉编码器，更准，约 1.3GB）。

六、两大检索技术 + 混合融合

6.1 BM25 —— 关键词检索

像高级版 Ctrl+F。你搜"ETF"，它能精准找到所有提到 ETF 的段落，且出现越多、越靠前的排越前。

擅长：专有名词精确匹配（"QDII"、"可转债"、"戴维斯双击"这类特殊词）。

短板：不懂同义词。搜"养老储蓄"，文档里写的是"退休规划"，它就找不到。

用到的库：rank_bm25（算法实现）+ jieba（中文分词）。

6.2 向量检索 —— 语义检索

像一个懂你意思的人。你说"养老储蓄"，虽然文档没这 4 个字，但它理解"养老"≈"退休规划"，就能找到相关段落。

怎么工作：① 每段文字变成一串数字（向量）→ ② 问题也变成向量 → ③ 比较相似度，越像越相关。

用到的技术：BGE-large-zh（编码）+ FAISS（极速向量搜索）。

短板：专有名词可能不准，会混入无关段落。

6.3 为什么两者要"混合"？

只用 BM25
"ETF" → 精准找到
"养老储蓄" → 找不到！
不认识同义词
+
只用向量
"养老储蓄" → 能找到！
"QDII" → 可能混入无关
专有名词不准

= 混合检索：两种方式同时搜，结果合并。各取所长，互补短板

6.4 RRF 融合 —— 怎么合并两路结果

合并公式叫 RRF（Reciprocal Rank Fusion，倒数排名融合）：

score(文档) = 1 / (k + BM25排名) + 1 / (k + 向量排名) 其中 k = 60
两个专家各自给文档排名。某个文档在两个专家那里都排第 1，它得分就最高；只在一个专家那里排第 1，得分就没那么高。相当于"两人都推荐的，才是真靠谱"。

score = 1/(60+rank) 累加"] V --> R R --> T["候选集 按得分降序"] style Q fill:#e74c3c,color:#fff style B fill:#3498db,color:#fff style V fill:#27ae60,color:#fff style R fill:#f39c12,color:#fff

七、分级记忆机制：短期 vs 长期

维度短期记忆长期记忆
存储位置内存（进程内）Elasticsearch
生命周期会话结束就消失跨会话永久保存
容量最近 5 轮（约 10 条）不限
用途维持当前对话连贯、判断追问相似历史问题检索、偏好标签、反馈统计
通俗比喻微信聊天记录（关了就没了）永久笔记本（下次还能翻）

短期记忆的"淘汰条件"

每轮 = 1 条用户问题 + 1 条助手回答 = 2 条记录。最多保留 5 轮 = 10 条。条件：当记录数超过 10 条时，从最旧的开始删除，直到不超过为止。

长期记忆的"启用条件"

长期记忆完全依赖 Elasticsearch。条件：ES 能 ping 通（连接成功）才会读写；连不上时，所有长期记忆操作静默跳过，不影响主流程。这也是为什么不启动 ES 也能正常问答，只是没有跨会话记忆。

八、核心概念速查

RAG 是什么？

Retrieval-Augmented Generation = 检索增强生成。

AI 生成回答之前，先从知识库里检索相关资料。就像"开卷考试"——先翻书找答案，再用自己的话写出来。

Embedding（向量嵌入）是什么？

把文字变成一串数字（向量）。意思相近的文字，数字也相近。

给每个人量身高体重。"180cm, 75kg"和"178cm, 72kg"很接近，说明体型相近。同理，"退休规划"和"养老储蓄"的向量也很接近。

Chunk（分块）为什么要做？

AI 一次看不了太长的文本（有 token 上限）。把长文档切成小段（每段 512 字、相邻重叠 64 字），每次只给 AI 看最相关的几段，既省又准。

一本 1000 页的百科全书，不能让 AI 每次都读完。切成一页页，它只需读最相关的 5 页。重叠 64 字是为了防止关键句子刚好被切在两页中间。

文档切分详解：切碎器具体怎么做

知识库支持四种文档格式，读取方式各不相同（实现见 retrieval/doc_parser.py）：

格式扩展名读取方式实现函数
纯文本 / Markdown.txt / .md按 UTF-8 读取（自动兼容 GBK）_read_file
Word 文档.docx逐段提取段落文字（跳过空段）_read_docx
PDF 文档.pdf逐页提取文字（内置 CJK 中文字体）_read_pdf

分块参数

每块最多 512 字，相邻两块重叠 64 字。参数来自 config/settings.py 的 CHUNK_SIZE / CHUNK_OVERLAP。

分隔符优先级（按顺序尝试）

双换行 → 单换行 → 句号 → 感叹号 → 问号 → 分号 → 逗号 → 空格 → 单字符

优先在"最粗"的分界处切（段落 > 句子 > 词 > 字），让每块尽量是一段完整的话，而不是从中间硬截断。

递归分割逻辑（_split_recursive）

  1. 找到当前文本里最高优先级的分隔符；
  2. 按它切成一串片段，能合并到 512 字以内就合并成一块；
  3. 某个片段仍超过 512 字，就换成下一级分隔符再切一次（递归）；
  4. 最后给相邻块加 64 字重叠。

重叠拼接（_add_overlap）

把上一块的末尾 64 字拼到下一块开头，防止关键句子恰好被切在两块中间。

哈希与 doc_id（_compute_hash）

doc_hash = md5(全文内容) // 内容变了 hash 就变，与文件名无关
doc_id = doc_hash + "_" + 分块序号（从 0 开始）

比如某文档 hash 为 7f313c…5fa9d、切成 2 块，则两块 id 分别为 …_0 和 …_1。评估测试集就是靠这个 id 精确指认"答案在哪一块"。

落盘位置

data/chunks/{doc_hash}/chunk_0.txt
data/chunks/{doc_hash}/chunk_1.txt
data/chunks/{doc_hash}/manifest.json // 来源文件、块数、长度等元数据

FAISS 是什么？

Facebook 开源的向量搜索引擎，能在海量向量里毫秒级找到最相似的 Top-K。

普通搜索是翻书找内容（慢），FAISS 是给每本书建了"指纹目录"，比指纹就能快速定位。

系统还配了一套"打分系统"，用来衡量检索和回答好不好。分两类：

类型指标含义是否需要 LLM

Keyword Coverage回答对期望关键词的覆盖率否

十一、常见问题

Q: 为什么不用 ChatGPT 直接回答？

A: 通用大模型不知道你公司/个人的内部资料。RAG 的价值是让 AI 只依据你自己的文档回答，并标注来源，不瞎编。

Q: BM25 和向量检索有什么区别？

A: BM25 是"关键词精确匹配"，搜"ETF"很准但不懂同义词；向量是"语义理解"，懂"养老储蓄≈退休规划"，但专有名词可能不准。两者混合互补。

Q: Reranker 和向量检索都是"理解语义"，有啥区别？

A: 向量检索是"粗筛"（从大量文档快速选候选），Reranker 是"精排"（对少量候选逐一仔细打分）。就像海选 vs 决赛。

Q: 短期记忆和长期记忆有什么区别？

A: 短期 = 微信聊天记录（关了就没了，只记当前会话 5 轮）。长期 = 笔记本（永久保存，跨会话还能翻）。

Q: 必须启动 Elasticsearch 吗？

A: 不必须。ES 只负责长期记忆，没启动时系统自动跳过，其他功能正常。就像没带笔记本也能聊天，只是记不住上次聊的什么。

Q: 为什么要分块（Chunk），不分块行不行？

A: AI 有"阅读量上限"（token 限制）。100 页的书不可能全塞给它。分块后只给它最相关的 5 页，既快又准。
